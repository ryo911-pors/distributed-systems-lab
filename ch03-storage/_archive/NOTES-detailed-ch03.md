# DDIA 3章 ストレージと抽出 — Lesson 1 (2026-08-19)

## 到達した思考の流れ
追記ログ → 読みが遅い → ハッシュ索引 → メモリが死ぬ/範囲クエリが死ぬ
→ SSTable(ソート) + 疎索引 → メモリ解決 → でも書き込み順がランダムだと詰む
→ **LSM-tree** (memtable + フラッシュ + compaction + WAL)

## 実測値 (5,000,000件 / 136MB)
| | grep | ハッシュ索引 | SSTable+疎索引 |
|---|---|---|---|
| 読み込み1件 | 378 ms | 0.0076 ms | 0.1148 ms |
| メモリ | ~0 | 718 MB | 16 MB |
| 索引エントリ | - | 5,000,000 | 5,000 |
| 範囲クエリ1万件 | - | 3.6 ms | 0.4 ms |
| 起動 | 0 | 1.12 s | 0.26 s |

## 覚えておく原則
1. 追記(sequential write)は速い。ランダム書き込みは遅い。これが全ての出発点
2. 索引 = 読みを速くする代わりに書きを遅くする取引。だからDBは索引を自動で張らない
3. ソートしておくと「疎索引」が可能になり、索引がメモリに収まる
4. どの手も必ず何かと引き換え。「何を払ったか」を必ず探す
5. 計測環境が結論を歪める (SSD+ページキャッシュはランダムアクセスに有利すぎる)

## 用語
- append-only log (追記専用ログ)
- byte offset (バイト位置)
- hash index (ハッシュ索引) / Bitcask
- SSTable = Sorted String Table (ソート済み文字列テーブル)
- sparse index (疎索引)
- memtable / compaction (コンパクション) / WAL = write-ahead log (先行書き込みログ)
- LSM-tree = Log-Structured Merge-Tree

## 次回
- LSM-tree を実装 (memtable + セグメント + compaction)
- そのあと B-tree と比較 → 書き込み増幅 (write amplification)
- 実物: RocksDB, LevelDB, Cassandra

## 未回答の宿題
- なぜ compaction が必要か? (やらないと何が起きるか)
- 削除はどう表現する? (ヒント: 追記しかできない世界で「消す」とは)

# Lesson 2: SSTable + 疎索引 のデメリット (実測)

## 1. 疎索引の粒度は「正解のないダイヤル」
| 間隔 | 索引エントリ | 索引メモリ | 読込1件 |
|---|---|---|---|
| 1 | 5,000,000 | 412.8 MB | 0.0119 ms |
| 10 | 500,000 | 40.9 MB | 0.0124 ms |
| 100 | 50,000 | 4.1 MB | 0.0226 ms |
| 1000 | 5,000 | 0.4 MB | 0.1220 ms |
| 10000 | 500 | ~0 MB | 1.0723 ms |
| 100000 | 50 | ~0 MB | 10.5564 ms |
→ 全項目で最良の設定は存在しない。うまみは間隔100〜1000。

## 2. 「無い」の証明が最も高くつく (read amplification / 読み取り増幅)
| 検索キー | 時間 | 走査セグメント |
|---|---|---|
| 最新セグメントにヒット | 0.0116 ms | 1/4 |
| 最古セグメントにヒット | 0.0448 ms | 4/4 |
| どこにも無い (miss) | 0.0451 ms | 4/4 |
→ 「ある」は途中で止まれるが「無い」は全走査。miss が常に最悪ケース。
→ この一点だけはハッシュ索引が強い(dictの空振りで一瞬)。
→ 対策が **Bloom filter (ブルームフィルタ)**。「絶対に無い」を高速判定するためだけに存在する。

## 3. SSTableは書き込みを受け付けられない ← 本命
| 操作 | 時間 |
|---|---|
| 末尾に追記 | 0.0725 ms |
| ソート順を保って1件挿入 | 552.9 ms (142MB全書き直し) |
| 差 | **7,622倍** |
→ SSTableは「DB」ではなく「読み取り専用のファイル形式」。
→ ソートで読みを解いた代償に、追記O(1)という最大の武器を失った。

## ハッシュ索引 vs SSTable (上位互換ではない、交換しただけ)
| | ハッシュ索引 | SSTable+疎索引 |
|---|---|---|
| 単一キー読込 | 0.0076 ms ◎ | 0.1148 ms |
| 存在しないキー | 一瞬 ◎ | 全セグメント走査 |
| メモリ | 718 MB | 16 MB ◎ |
| 範囲クエリ | 3.6 ms | 0.4 ms ◎ |
| 書き込み | 追記O(1) ◎ | 不可能 |

## この3つが LSM-tree の設計仕様書
| デメリット | LSM-treeの回答 |
|---|---|
| 3. ソート順書き込みが激遅 | **memtable** (ソートはメモリ上、ディスクへは順次書き出すだけ) |
| 2. セグメント増でmissが重い | **compaction** で統合 + **Bloom filter** でmissを弾く |
| 1. 粒度のダイヤル | 消えない。残る設計判断 (RocksDBのチューニング項目) |

# Lesson 3: なぜ間隔を広げると読みが遅くなるのか

## 仕組み
疎索引は「目的のキー」ではなく「近くの目印」までしか連れて行かない。
目印へ1回seekした後、**前方へ順次スキャン**して目的のキーを探す。
→ 間隔 = ジャンプ後にめくる最大距離。間隔10倍 = めくる距離10倍。

紙の辞書のツメと同じ。ツメがA-Zの26個だけなら「S」を開いてから延々めくる。
ツメを増やせばめくる量は減るが、小口がツメだらけになる(=メモリ)。

## 検証したモデル (誤差 最大9.3%)
```
読込時間 = 0.0121 ms (固定費) + 0.1007 µs × スキャン件数
```
| 間隔 | 実スキャン件数 | 実測 | 予測 | 誤差 |
|---|---|---|---|---|
| 1 | 1 | 0.0122 ms | 0.0122 ms | 0.0% |
| 10 | 10 | 0.0120 ms | 0.0131 ms | 9.3% |
| 100 | 100 | 0.0207 ms | 0.0222 ms | 7.3% |
| 1000 | 1,000 | 0.1078 ms | 0.1129 ms | 4.7% |
| 10000 | 10,000 | 1.0042 ms | 1.0196 ms | 1.5% |
| 100000 | 100,000 | 10.0864 ms | 10.0864 ms | 0.0% |

## なぜグラフが「平ら → 直線」の2段になるか
読込時間は2つの費用の和:
- 固定費 0.0121 ms (open/seek/関数呼び出し。件数に無関係)
- スキャン費 0.1007 µs × 件数

釣り合う点 = 約120件 (0.1007µs × 120 ≈ 12.1µs)
- 間隔 < 120 : スキャン費が固定費に埋もれる → 狭めても速くならない(平ら)
- 間隔 > 120 : スキャン費が支配的 → 間隔に正比例(直線)
→ 「うまみが100〜1000」だったのはこの分岐点があるから。

## 現実のDB
件数ではなく**ディスクのブロックサイズ(4KB等)**に合わせて目印を置く。
1回の読み取り単位に収まる範囲のスキャンは実質タダ、という発想。
固定費とスキャン費の分岐点をハードウェアの単位に合わせている。

## 学んだ型
数字が出たら「固定費 + 変動費」に分解して線形モデルを立て、実測と突き合わせる。
モデルが合えば仕組みを理解できた証拠。合わなければ見落としがある。

# Lesson 4: 「SSTableは書き込めない」の正確な意味

## 「不可能」は不正確。正しくはこう
バイトを書くこと自体はできる(ただの追記ファイル)。壊れるのは**ソート済みという前提**。
そして **失敗ではなく「静かな嘘」になる**。

## 実験: ソート済みSSTableの末尾に 00000042 を追記した
```
索引の末尾5件      : [00099600, 00099700, 00099800, 00099900, 00000042]
索引はソート済みか : False
bisectが返した位置 : 0 -> 目印 00000000
```
1. 追記は成功。例外なし
2. 索引がソート済みでなくなる
3. bisect は「ソート済み」が前提の関数 → 前提が崩れて位置0を返す
4. 00000000〜00000099 をスキャン → **古い** 00000042 が見つかり即return
5. 追記した LATEST_VALUE はファイル末尾。**到達しない**
→ get() は古い値を正常な顔で返し続ける。

## なぜこれが最悪の失敗か
- 例外が出ない / クラッシュしない / ほとんどのキーは正常に読める / テストも通る
- 気づくのは数週間後の本番。「なぜかデータが古い」
- **即クラッシュしてくれるほうがマシ**

## 解: SSTableを immutable (不変) にする
一度ディスクに書いたセグメントは二度と変更しない、というルールにする。
- 書き込み → memtable (メモリ上の平衡木) へ
- memtable満杯 → **新しい**セグメントとして書き出す。既存には触らない
- 更新も削除も → 新しいセグメントに追記するだけ。古いのは放置
- 溜まったら → compaction で**新しいファイルを作り**古いのを丸ごと捨てる
→ 「変更」という操作がシステムのどこにも存在しない

## 不変性が連れてくるおまけ
- **読み込みにロック不要** (誰も書き換えないので読者は何人でも安全)
- **クラッシュに強い** (書きかけは捨てればいい。既存データは壊れようがない)
- **compactionが可能** (読者がいる最中でも裏で新ファイルを作り、完成後に差し替え)

→ LSM-treeの構成要素の根っこは「不変性」という1つの設計判断。
   memtableもcompactionも、「セグメントを絶対に書き換えない」と決めたから必要になった。

## 今回の教訓 (自分への)
Lesson 3で立てた予想(「読めなくなる」「無関係なキーも壊れる」)は外れた。
実測が訂正した。仮説は外れてよく、数字を見て直せるかどうかが全て。

# Lesson 5: セグメントを消す判断は何か

## 疑問 (自分で立てた良い問い)
seg1の半分はseg5で更新済み。でも残り半分はseg1にしか無い。
→ seg1を消したら半分が失われる。じゃあ消せないのでは?

## 答え: compactionは「消す」操作ではなく「マージして作り直す」操作
```
NG: seg1を消す → 半分が失われる
OK: seg1 + seg5 をマージして seg6 を作る → seg1もseg5も消す
```
順序が逆。「消せるか判断して消す」のではなく「**引き継いでから消す**」。

## 実測 (seg1=100件, seg5=偶数50件を更新)
- seg1にしか無いキー(奇数50件) → seg6に救出された
- 古い値50件 → 捨てられた
- 2,685 bytes → 1,790 bytes (33%削減)、ファイル2本→1本

## 削除できる条件 (2つ)
1. 中身が新しいセグメントに引き継ぎ済み (compaction完了)
2. **現在そのファイルを読んでいる読者がいない** → 参照カウントで管理
   これが安全にできるのは immutable だから(読者は読み始めた版を読み続ければいい)

## マージが安い理由 = ソートの真の見返り
両方ソート済みなので先頭から並走して舐めるだけ:
- 時間 O(n+m) / **メモリ一定** / **順次読み+順次書き**(ランダムアクセス0)
- → 100GB同士を8GBマシンでマージできる

| ソートで得たもの | 効果 |
|---|---|
| 疎索引 | メモリ 718MB → 16MB |
| 範囲クエリ | 連続読みになる |
| **効率的なマージ** | **compactionが現実的 = LSM-treeが成立する** |
→ 3つ目がなければセグメントは増える一方で何も消せず詰む。

## どれをマージするかは方針 (compaction strategy)
- **size-tiered**: 同サイズ同士をマージ。書き込み軽いが読むセグメントが増えがち
- **leveled**: 階層を作り下ほどN倍大きく。読み安定だがマージ回数増で書き込み重い
→ RocksDB/Cassandraの設定項目。デメリット1「消えないダイヤル」がここにも出る。

## 次の問い (宿題2の本番)
削除は **tombstone (墓標)** = 「このキーは消えた」印を新セグメントに書く。
では **その tombstoneはいつ消していいのか?**
compactionでtombstoneを単純に捨てると、**もっと古いセグメントに残る古い値が復活する**。
→ Lesson 5と同じ構造の問題。

# Lesson 6: compaction は /compact と似てるのか

## 構造的な対応は本物
| LSM-tree | 会話 / /compact |
|---|---|
| 追記専用ログ | 会話履歴(過去のターンは書き換わらない) |
| セグメントは不変 | 過去のやり取りは編集されない |
| 新しい値が古い値を上書き | 後の発言が前の発言を無効化 |
| メモリ上限 | コンテキストウィンドウ上限 |
| 閾値超えでcompaction | 逼迫したら /compact |
| マージして新セグメント、古いのを捨てる | 要約を作り元のターンを捨てる |
→ 「追記され続ける不変のログ + 有限容量 + 古い情報を畳む」骨格は同じ。

## 決定的な違い: 無損失(lossless) vs 有損失(lossy)
- LSM: 置き換えられた古い値だけ捨てる。生きてる値は1バイトも変わらずコピー。
  **compaction前後で get(k) の結果が一致することが設計上の不変条件**
- /compact: 要約は近似。情報が本当に失われ、何が失われたかも分からない

## なぜこの差が出るか
1. **キーの有無**: LSMは「同じキー→新しい方」で機械的に判定できる。
   会話にはキーが無く「もう不要か」は文脈依存 = 原理的に機械判定不可
2. **ソート順の有無**: LSMのO(1)メモリ並走マージはキー順ソートが前提。
   会話は時系列順であってキー順ではないので、あの安いマージが使えない

## DDIA世界での正確な対応物
- **Kafkaのlog compaction** = キーごとに最新だけ残す。LSMとほぼ同じ、無損失
- **時系列DBのロールアップ(downsampling)** = 1秒粒度を1分平均に畳む。**有損失**
→ /compact は「**キーのない世界でやるロールアップ**」が一番近い

## LLM推論にも同じ問題が出る (本命への接続)
- **vLLMのKV cache**: 生成が進むほどKVが増え、GPUメモリは有限 → eviction判断
  PagedAttention = この問題にOSのページングの発想を持ち込んだもの
- **sliding window attention / attention sink** = コンテキストのcompaction戦略そのもの
  「古いトークンを捨てる、ただし最初の数トークンは残す」= size-tiered/leveledと同じ構造

→ 「有限の容器に増え続ける履歴をどう畳むか」は領域を超えて再出現するパターン。
