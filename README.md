# 分散システム障害再現ラボ

『データ指向アプリケーションデザイン』(DDIA) の主張を、**実際に測定し、壊して再現する**記録。

読書ノートではない。各章に必ず「**自分の予想が外れた点**」を残している。

---

## 3章 ストレージエンジン（完了）

追記ログ → ハッシュインデックス → SSTable → LSM-tree → Bツリー を、
すべて自前実装して測定した。実験コード16本、すべて再実行可能。→ [`ch03-storage/`](ch03-storage/)

### 測ったもの

| 測定 | 結果 |
|---|---|
| メモリ vs ディスクのレイテンシ | 0.68 µs vs 114.58 µs → **168倍** |
| 同じ78MBの書き込み: シーケンシャル vs ランダム | 31 ms vs 2,132 ms → **68倍** |
| Bツリーの書き込み増幅（20バイトの更新） | 4,096 バイト書く → **206倍**（ページ分割時 615倍） |
| Bloom filter で100万キーの存在判定 | `set` 68.7 MB → **1.14 MB**（60分の1）。偽陰性 **0件** |
| 疎索引によるメモリ削減 | 718 MB → **16 MB** |
| LSM-tree の tail latency | 中央値 0.13 ms / p99 0.15 ms / **p99.5 で 50 ms（385倍の崖）** |

### 予想が外れた点

- **ソート済み前提を壊した SSTable は、エラーを出さずに古い値を返した。**
  「読めなくなる」と予想していたが、実際は*静かに嘘をつく*。二分探索が前提を破られたときと同じ壊れ方。
- **索引の粒度を4096バイトより細かくしても、読み取りは1バイトも速くならない。**
  索引を41倍持ってもディスクはブロック単位でしか読めない。メモリだけが増える。
- **最初の計測は2回とも汚染されていた。**
  128Bが4KBより遅く見えた（初回ループのウォームアップ）／WALがmemtableより速く見えた（memtableのサイズが違った）。
  → 以降、ウォームアップと順序ランダム化を規約にした。

## 5章 レプリケーション（進行中）

本物の PostgreSQL でリーダー1 + フォロワー2 を Docker Compose で構成し、
**非同期レプリケーションで「成功」と返された書き込みが、リーダー障害で実際に消えるのを再現する。**

## 8章 分散システムの問題（予定）

`docker network disconnect` でネットワークを分断し、**スプリットブレイン**を発生させる。
`tc netem` で遅延注入、コンテナの時計をずらして clock skew、`SIGSTOP` で GC ストップザワールドを再現。
