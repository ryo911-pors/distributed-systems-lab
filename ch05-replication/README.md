# ch05 レプリケーション — PostgreSQL を壊して測る

DDIA 5章の主張を、本物の PostgreSQL（リーダー1 + フォロワー2）で検証する。

**環境の限界を先に書いておく**: 3つのコンテナは同じ MacBook のメモリ・ディスク・CPU を
共有している。**本物の3台構成ではない。** ネットワークとレプリケーションプロトコルは本物。
地理的レイテンシとハードウェア故障は再現できない。

| 実験 | 対応節 | 状態 |
|---|---|---|
| ① 同期 vs 非同期の書き込みレイテンシ | 5.1.1 | 未 |
| **② 稼働中にフォロワーを追加** | **5.1.2** | **✅ 完了** |

| ⑤ 書いた直後に古い値が返る | 5.2 | 未 |

## 実験② 稼働中にフォロワーを追加する

### 1. 本の主張

> データベースをロックすれば（すなわち書き込みを禁止すれば）、ディスク上のファイルの一貫性を
> 保つことはできますが、それは高可用性という目標には反します。**ありがたいことに、フォロワーの
> セットアップは通常ダウンタイムなしに行えます。**
>
> — DDIA 5.1.2「新しいフォロワーのセットアップ」(PDF p.189)

手順として本が挙げるのは4段階。**スナップショット + その位置 + それ以降のログ**で、
動いているデータベースから一貫した状態を切り出す。

### 2. 再現手順

```bash
# 1. 環境を立てる（Docker Desktop が起動していること）
cd ch05-replication
docker compose up -d leader follower1

# 2. Python 環境（psycopg が必要）
python3 -m venv ../.venv && ../.venv/bin/pip install "psycopg[binary]"

# 3. 実験を走らせる
../.venv/bin/python experiments/02_add_follower.py
```

ポートは **15432 / 15433 / 15434**（5432 は開発機のネイティブ PostgreSQL と衝突するため）。

**測り方**: リーダーへ INSERT を打ち続けるスレッドを1本立て、その最中に follower2 を
`docker compose up` で追加する。1件ごとに（時刻・所要ミリ秒・成否・失敗理由）を記録する。
同時に別スレッドがリーダーの `pg_stat_replication` を 0.25 秒ごとに読み、
各フォロワーの遅れを記録する。生データは `results/*.csv` に保存され、集計はあとから
何度でもやり直せる（実験を測り直さずに済ませるため）。

区間の設計:

```
[捨てる 3秒][追加前 5秒][追加 ~45秒][追加後 30秒]
 ~~~~~~~~~~
 接続確立の汚染を捨てる区間。集計に入れない
```

### 3. 実測結果

```

失敗した書き込み :       0 件
follower2 の追加 :    44.6 秒

書き込みレイテンシ (ms)
                    件/秒     中央値     p95     p99   p99.9     最大
  追加前            5,502      0.17    0.26    0.39    0.52    1.65
  追加中            5,430      0.17    0.27    0.40    0.62   15.29
  追加後            4,267      0.22    0.33    0.49    0.69   12.77

follower2 の遅れ（追加完了を 0 秒とする）
      経過          状態      遅れ(MB)   遅れ(秒)
     0.1s   streaming        0.00      0.000
    29.7s   streaming        0.00      0.000     ← 30秒間ずっとゼロ

各ノードが持っている行数
  leader     414,165 行

```

**本の主張は支持された。**
41万件を流し続けたまま1台追加して、**失敗は0件**。44.6秒の追加作業の最中も、
スループット・中央値・p99.9 のすべてが追加前と変わらなかった。

follower2 は自分が存在しなかった時期の書き込みも保持している。
スナップショットで土台を受け取り、コピー中に発生した分は WAL ストリームで受け取ったため。

### 4. 食い違い / 予想外だったこと

**① 比較対象が存在しないまま、3回ぶん結論を書いていた**

最初の設計は `[捨てる 3秒][追加 18秒][追加後 3秒]` で、**ウォームアップの終わりと追加の開始が
同時刻**だった。捨てる処理が「追加前」を丸ごと食べていた。

```
「それ以外」に入った 12,315 件の時刻: 3.0 秒 〜 24.0 秒
→ 追加より前のデータが 1 件も入っていない
```

つまり「追加中 vs それ以外」は、実際には「**追加中 vs 追加後**」を比べていた。
何と比べているのかを確認せずに3回結論を書いていた。

原因は、**ウォームアップ（測定の立ち上がり）とベースライン（比較対象）を混同していた**こと。
接続コストがかかるのは1件目だけで（5.097ms、2件目 1.315ms、4件目には 0.345ms）、
3秒ぶん捨てるうち実際に汚染されているのは最初の数ミリ秒だけだった。
残り約12,000件は、捨てる必要のない定常状態のデータだった。

追加前の区間を置いたら、それまでの結論はひっくり返った。

**② 高そうな操作がタダで、安そうな操作が22%を持っていった**

```
basebackup が走っている44.6秒間   5,430 件/秒   0.17 ms   ← 影響が測れない
3台目が streaming になった後      4,267 件/秒   0.22 ms   ← 22%減、恒久的
```

**44.6秒かけてデータ全体をネットワーク越しにコピーする処理**は、リーダーのスループットを
まったく落とさなかった。落ちたのは**コピーが終わって定常状態に入ってから**で、しかも戻らない。

「テーブルが育ったから遅くなっただけでは」を排除するため、2秒ごとの推移を見た:

```
秒     累計行数     件/秒   中央値
 0     10,877     5,438    0.17   ← ほぼ空
50    283,602     5,470    0.17   ← 28万行。まったく変わらない
──────────────────────────────── follower2 の追加が完了
54    300,604     4,272    0.22
80    411,476     4,258    0.22   ← 41万行。ここも平ら
```

**0行から28万行まで育っても速度は変わらなかった**ので、行数のせいではない。
変化はなだらかな坂ではなく**段差**で、位置は `add_end` と一致していた。

「まだ追いつき中だから遅いのでは」も、`pg_stat_replication` に直接聞いて排除した。
follower2 の遅れは追加完了の 0.1 秒後から 30 秒間ずっと **0.00 MB / 0.000 秒**だった。

**ただしこれは断定できない。** 3つの PostgreSQL は同じ Docker VM の同じ CPU を分け合っている。
follower2 が毎秒4,300件を再生する CPU は、リーダーが使えたはずの CPU でもある。
**「レプリケーション固有のコスト」なのか「1台のMacでのCPU取り合い」なのかは未検証。**
本物の分散システムはノードごとに別のハードウェアを持つので、そのまま一般化はできない。

本は「追加はダウンタイムなしで行える」とは書いているが、**追加した後に恒久的なコストが乗る**
ことには触れていない。

**③ bash 版が測っていたのは、データベースの速度ではなかった**

同じ実験を最初 bash で書いたところ **1,321件**しか流れず、Python 版では **156,042件**（118倍）。
原因は bash 版が1 INSERT ごとに `docker compose exec` と `psql` のプロセスを起動していたこと。

接続コストを実測すると:

```
接続を張って切るだけ  3.476 ms
INSERT 自体          0.255 ms     ← 本来の仕事は全体の 7%
```

**本来の仕事の14倍が、準備と後片付けに消えていた。**

**④ 「最大値が4倍悪い」と結論しかけたが、間違いだった**

p99 までしか出していなかったとき、最大値だけが 28.96ms vs 7.55ms と差があり、
「フォロワー追加はディスクI/Oを奪って最悪ケースを悪化させる」と書きかけた。

p99.9 を出したら **0.63 vs 0.58** でほぼ差がなかった。最大値に該当するのは数件で、
**tail に厚みはなかった**。1点の外れ値を傾向として語りかけていた。

**⑤ 2台のフォロワーが、リーダーからは区別できなかった**

`pg_stat_replication` を読んだら、両方とも `application_name` が `walreceiver` で
どちらがどちらか分からなかった。`cluster_name` を設定すると walreceiver の名前になるので、
compose に `hostname: follower1` を足して解決した。

**⑥ ポート 5432 が奪われていた**

`localhost:5432` に接続したら `role "postgres" does not exist` が返ってきた。
開発機に別の PostgreSQL が常駐していて、Docker より優先して bind されていた。
コンテナが公開ポートを取れていても、**より具体的なアドレスに bind した既存プロセスが勝つ**。

## 実験③ フォロワーを落として、戻す

### 1. 本の主張

> ローカルディスク上では、各フォロワーは自分がリーダーから受信したデータ変更のログを保持します。
> 仮にフォロワーがクラッシュして再起動した場合、あるいはリーダーとフォロワー間のネットワークが
> 一時的に切れてしまった場合でもリカバリは容易です。**フォロワーは障害発生前に最後に処理した
> トランザクションをログから判断できるので、フォロワーはリーダーに接続し、接続が切れた後に
> 生じたすべてのデータ変更を要求できます。**
>
> — DDIA 5.1.3.1「フォロワーの障害：キャッチアップリカバリ」(PDF p.167)

**この実験が答える問い**: フォロワーが戻ってきたとき、リーダーは
(A) 最初からデータを全部送り直すのか / (B) 止まっていた間の分だけを送るのか。

(A) だったら、1TB のデータベースで5秒ネットワークが切れるたびに 1TB の再コピーになる。
**レプリケーションが実用になるかどうかが、ここにかかっている。**

### 2. 再現手順

```bash
cd ch05-replication
docker compose up -d
../.venv/bin/python experiments/03_kill_follower.py
```

**測り方**: 書き込みを流したまま `docker compose stop follower1` で止め、10秒書き続けてから
`start` で戻す。`pg_stat_replication` を 0.05 秒ごとに読み、`byte_lag` が 0 に戻るまでの
時間を測る。区間は `[捨てる 3秒][停止前 5秒][停止 10秒][追いつき][復帰後 5秒]`。

**②との決定的な違いは `rm` を使わないこと。** `follower/entrypoint.sh` は起動時に
`PGDATA` が空かどうかで分岐する。② は `rm -v` で中身を消したのでスナップショット取得の枝を、
③ は `stop`/`start` だけなので中身が残り、ログで追いつく枝を通る。

### 3. 実測結果

```

失敗した書き込み       :       0 件
停止中に受け付けた書込 :  56,880 件   ← follower1 が取りこぼした分
起動 → 接続受付       :    0.31 秒
起動 → 遅れ 0         :    0.34 秒
再接続後の初回観測の遅れ:   10.57 MB (起動 +0.12秒)

follower1 のコンテナログ
  「スナップショットを取得します」    : False
  「コピーせずログで追いつきます」    : True

書き込みレイテンシ (ms)
                    件/秒     中央値     p95     p99   p99.9     最大
  停止前            4,293      0.22    0.35    0.49    0.65    5.24
  停止中            5,345      0.17    0.27    0.41    0.60    6.17
  追いつき中         3,773      0.21    0.56    0.87    4.60    5.07
  復帰後            4,121      0.23    0.36    0.51    0.66    7.86

各ノードが持っている行数
  leader     113,435 行
  follower1  113,435 行
  follower2  113,435 行
```

**答えは (B)。本の主張は支持された。**

```
空から作る（②）      44.6 秒
ログで追いつく（③）    0.34 秒     ← 131倍速い
```

5.7万件・10.57MB ぶん遅れた状態から **0.34秒**で追いついた。コンテナログも
「コピーせずログで追いつきます」の枝を通ったことを示している。
**リーダーは最初から送り直していない。**

### 4. 食い違い / 予想外だったこと

**① ②の発見が、逆向きの操作で再現された**

これは狙っていなかった。

```
停止前   4,293 件/秒   フォロワー2台
停止中   5,345 件/秒   フォロワー1台   ← 25%速い
復帰後   4,121 件/秒   フォロワー2台   ← 戻った
```

② では「フォロワーを**足したら** 22% 遅くなった」。③ では「フォロワーを**外したら** 25% 速く
なった」。逆向きの操作で同じ量が出た。

さらに重要なのは、**テーブルは一貫して増え続けているのに、スループットが下がって・上がって・
下がっていること。** 行数が原因なら単調にしか動けない。
**② で残していた「テーブルが育ったせいでは」という疑いは、これで完全に消えた。**

（3ノードが同じ Docker VM の CPU を共有している件は、依然として未検証のまま）

**② 「接続を受け付けた」と「追いついた」の差が測れなかった**

```
起動 → 接続受付   0.31 秒
起動 → 遅れ 0     0.34 秒
```

差が **0.03秒**しかない。10.57MB の WAL をその間に適用したことになる。
サンプリング間隔が 0.05 秒なので、**この解像度では「本当に速い」のか「測れていない」のかを
区別できない。未確定。**

② では「接続を受け付けた ≠ 追いついた」を強調したが、③ の規模ではほぼ同時だった。

**③ 停止中のフォロワーは、リーダーからは「遅れている」ように見えない**

止まっているフォロワーは `pg_stat_replication` から**行ごと消える**。
「10秒間でどれだけ離れたか」をリーダー側から観測する手段が無い。

そのため、遅れの大きさは
- **書き込み件数**（Writer が記録した 56,880 件）
- **再接続直後に初めて観測できた byte_lag**（10.57 MB）

の2つで代用している。**停止中の最大の遅れは、この実験では観測できていない。**

**④ 「取りこぼした分だけ送る」を成立させているのは、フォロワー側のディスク**

本文の「フォロワーは自分がリーダーから受信したデータ変更のログを保持します」が効いている。
③ で `rm` を使わなかったのは、**この「保持しているログ」を消さないため**。
消せば ② と同じ 44.6 秒コースになる。同じ `entrypoint.sh` の別の枝を通るだけで、
所要時間が 131 倍変わる。

## ファイル構成

```
compose.yaml                    リーダー1 + フォロワー2
leader/init-replication.sh      replicator ロール + pg_hba.conf に1行追記
follower/entrypoint.sh          pg_basebackup でスナップショットを取得して standby 起動
experiments/lab.py              全実験の共通部品（下記）
experiments/02_add_follower.py  実験②の手順
experiments/03_kill_follower.py 実験③の手順
results/                        生データ（CSV + イベント時刻の JSON）
```

`lab.py` に置いてあるもの:

| | |
|---|---|
| `Writer` | INSERT を打ち続け、1件ごとに時刻・所要時間・成否・失敗理由を記録するスレッド |
| `LagSampler` | `pg_stat_replication` を定期的に読み、各フォロワーの遅れを記録するスレッド |
| `docker()` | `docker compose` の実行。失敗したらその場で止まる |
| `wait_until_ready()` | ノードが接続を受け付けるまで待つ。待ちきれなければ例外 |
| `save()` / `load()` | 生データの保存と読み戻し。集計を変えても測り直さずに済む |
